LE Client¶

The functions to scan for Bluetooth LE devices, connect to them as a GATT client, and discover, read, write and subscribe to their services, characteristics and descriptors.

A connection, and every service, characteristic and descriptor on it, is addressed by an opaque handle, never by its UUID, so two attributes that share a UUID get their own handles. Discovery goes one level at a time: bluetooth_le_services_discover on a connected connection, then bluetooth_le_characteristics_discover on a service, then bluetooth_le_descriptors_discover on a characteristic. The getters, such as bluetooth_le_service_get_count and bluetooth_le_service_get_at, list each level in the order discovery found it. Every handle discovered on a connection is retired when the connection ends.

The bytes of a read or a notification arrive as a value handle and a size, and are copied into a buffer with bluetooth_value_fetch. A call that fails before it starts returns a BluetoothError (or 0 for bluetooth_le_connect) and never calls its callback; bluetooth_last_error_message gives the reason.

bluetooth_le_is_supported¶

This function checks whether this platform and its Bluetooth adapter can act as a Bluetooth LE central: scan for LE devices and connect to them. It returns false before bluetooth_initialize has been called and on a device with no Bluetooth LE hardware, and gives the same answer as bluetooth_feature_is_supported with BluetoothFeature.LeCentral.

Note

On Windows the answer comes from the adapter, so call this function after bluetooth_initialize.


Syntax:

bluetooth_le_is_supported()


Returns:

Boolean

true if Bluetooth LE central is supported, otherwise false.


Example:

if (!bluetooth_le_is_supported())
{
    show_debug_message("Bluetooth LE is not available on this device");
}
The above code checks for Bluetooth LE support and writes a message to the output log when it is not available.

bluetooth_le_scan_start¶

This function starts scanning for Bluetooth LE devices. Every device the scan finds enters the shared device cache and fires the callback set with bluetooth_set_callback_device_found once; later advertisements from the same device update its name, RSSI and advertisement, which bluetooth_device_get_name, bluetooth_device_get_rssi and bluetooth_device_get_advertisement return. When the scan stops, whether you stopped it or it failed, the callback set with bluetooth_set_callback_scan_stopped is called.

The given filters array holds BluetoothLeScanFilter structs. An empty array reports every device; otherwise a device enters the cache once its advertisement matches any one of the filters. A filter matches when every field it sets matches. The given active argument asks for scan-response packets as well as advertisements; false scans passively only where BluetoothFeature.LePassiveScan is supported (Windows), and is ignored elsewhere.

A start while a scan is already running returns BluetoothError.Ok, starts nothing new and keeps the running scan's filters: stop the scan first to change them. While the Bluetooth state is still BluetoothState.Unknown the scan starts once the radio is ready.

If the scan cannot start, the function returns a BluetoothError other than Ok: NotInitialized, InvalidArgument for a filter that sets no field, a malformed UUID or a company_id outside 0-65535, PermissionDenied when the Bluetooth permission is missing or was refused, BluetoothDisabled when the radio is off, NotSupported when there is no Bluetooth LE hardware, or OperationFailed when the platform refused to start. The reason is in bluetooth_last_error_code and bluetooth_last_error_message, and no scan callback is called.

Note

Android filters in the Bluetooth stack, scans in low-latency mode and allows 5 scan starts per 30 seconds: a sixth starts but finds nothing. It also pauses unfiltered scans while the screen is off, and on Android 6 to 11 a scan returns PermissionDenied while the system Location setting is off.

Note

Apple and Android always scan actively. iOS needs every filter to set service_uuid to scan in the background.


Syntax:

bluetooth_le_scan_start(active, filters)
Argument Type Description
active Boolean Whether to request scan-response packets (an active scan).
filters Array of BluetoothLeScanFilter The filters a device must match one of, or an empty array for every device.


Returns:

BluetoothError


Example:

bluetooth_set_callback_device_found(function(_device)
{
    show_debug_message($"Found {bluetooth_device_get_name(_device)}");
});

var _filter = new BluetoothLeScanFilter();
_filter.service_uuid = "180d";

var _error = bluetooth_le_scan_start(true, [_filter]);
if (_error != BluetoothError.Ok)
{
    show_debug_message($"Scan did not start: {bluetooth_last_error_message()}");
}
The above code first sets the callback that is called for each device the scan finds, which writes the device's name to the output log. It then creates a BluetoothLeScanFilter that matches devices advertising the Heart Rate service (0x180D) and starts an active scan with it. If the scan could not start, the reason is read with bluetooth_last_error_message.

bluetooth_le_scan_stop¶

This function stops the running Bluetooth LE scan. When a scan was running, the callback set with bluetooth_set_callback_scan_stopped is called once with BluetoothError.Ok. A stop while no scan is running returns Ok and calls nothing.

The function returns BluetoothError.NotInitialized before bluetooth_initialize, and on Windows OperationFailed when the platform could not stop its scanner; the scan counts as stopped in that case too. The reason is in bluetooth_last_error_message.


Syntax:

bluetooth_le_scan_stop()


Returns:

BluetoothError


Example:

if (bluetooth_le_scan_is_running())
{
    bluetooth_le_scan_stop();
}
The above code stops the Bluetooth LE scan if one is running.

bluetooth_le_connected_devices_query¶

This function lists the Bluetooth LE devices that are connected to this system, by this game or by another app, without a scan. The callback is called once with an array of device handles. A device that is not in the device cache yet enters it without firing the callback set with bluetooth_set_callback_device_found. You can pass a handle from the list to bluetooth_le_connect.

Every UUID in the given service_uuids array is checked first. If the query cannot start, the function returns a BluetoothError other than Ok: NotInitialized, InvalidArgument for a malformed UUID, PermissionDenied, BluetoothDisabled or NotSupported as for bluetooth_le_scan_start, and the callback is never called. The reason is in bluetooth_last_error_message.

Note

Android and Windows list every connected LE device and ignore service_uuids. Apple can only list the devices that expose one of the given services: an empty array is InvalidArgument there, and the radio must already be on (BluetoothDisabled otherwise).

This function operates asynchronously, which means that it does not immediately return the requested result. Instead, upon completion of the task, it will trigger the Callback.


Syntax:

bluetooth_le_connected_devices_query(service_uuids, callback)
Argument Type Description
service_uuids Array of String The service UUIDs a device must expose one of (used on Apple only).
callback Function The function to call once with the list of connected devices.


Returns:

BluetoothError


Triggers:

Callback

Called once, with the connected devices or the reason the query failed.

Key Type Description
error_code BluetoothError BluetoothError.Ok if the query succeeded, otherwise the reason it failed.
message String A description of the failure, or an empty string on success.
devices Array of Real The handles of the connected devices, empty on failure.


Example:

var _error = bluetooth_le_connected_devices_query(["180d"], function(_error_code, _message, _devices)
{
    if (_error_code != BluetoothError.Ok)
    {
        show_debug_message($"Query failed: {_message}");
        return;
    }
    for (var _i = 0; _i < array_length(_devices); _i++)
    {
        show_debug_message($"Connected: {bluetooth_device_get_name(_devices[_i])}");
    }
});

if (_error != BluetoothError.Ok)
{
    show_debug_message($"Query did not start: {bluetooth_last_error_message()}");
}
The above code asks for the LE devices connected to the system that expose the Heart Rate service. The callback writes the reason to the output log if the query failed, otherwise the name of each device it found. If the query could not start at all, the reason is read with bluetooth_last_error_message and the callback is never called.

bluetooth_le_connect¶

This function starts a GATT connection to the given Bluetooth LE device, which must have been found by a scan, listed by bluetooth_le_connected_devices_query or looked up with bluetooth_device_from_id. It returns a connection handle straight away, before the device has answered, and the callback is called once when the connection is made or fails.

The function returns 0 when the connect could not be started, and the reason is then in bluetooth_last_error_code and bluetooth_last_error_message: NotInitialized, InvalidHandle for a device handle that is not valid, InvalidArgument for a Classic device or one with no usable address, PermissionDenied, BluetoothDisabled, NotSupported, or Busy when the device already has a connection. In that case the callback is never called.

A device that does not answer within 15 seconds fails with BluetoothError.Timeout, and one that refuses or whose link fails with ConnectionFailed. You can cancel a connect that is still in progress by passing the returned handle to bluetooth_le_disconnect, and the callback is then called once with BluetoothError.ConnectionFailed. bluetooth_shutdown fails a connect still in progress with NotInitialized. A connect that fails retires its handle.

Note

A device can only have one client connection at a time, whether it is still connecting or already connected.

Note

On Apple the connect also returns 0 with NotFound for a device that CoreBluetooth no longer knows (scan for it again), and with PermissionDenied until bluetooth_permission_request has been answered.

This function operates asynchronously, which means that it does not immediately return the requested result. Instead, upon completion of the task, it will trigger the Callback.


Syntax:

bluetooth_le_connect(device, callback)
Argument Type Description
device Real The handle of the LE device to connect to.
callback Function The function to call once the connection is made or fails.


Returns:

Real

The new connection handle, or 0 if the connect did not start.


Triggers:

Callback

Called once, when the connection is made, fails or is cancelled.

Key Type Description
error_code BluetoothError BluetoothError.Ok if the device is connected, otherwise the reason it is not.
message String A description of the failure, or an empty string on success.
connection Real The connection handle that bluetooth_le_connect returned.
device Real The handle of the device.


Example:

connection = bluetooth_le_connect(device, function(_error_code, _message, _connection, _device)
{
    if (_error_code != BluetoothError.Ok)
    {
        show_debug_message($"Connect failed: {_message}");
        connection = 0;
        return;
    }
    show_debug_message("Connected, discovering services");
    bluetooth_le_services_discover(_connection, on_services);
});

if (connection == 0)
{
    show_debug_message($"Connect did not start: {bluetooth_last_error_message()}");
}
The above code starts a connection to the device stored in the instance's device variable and keeps the returned handle in connection. When the callback reports a failure the handle is cleared; on success the services of the device are discovered next with bluetooth_le_services_discover, which calls the instance's on_services function. If the connect could not be started at all, the returned handle is 0 and the reason is read with bluetooth_last_error_message.

bluetooth_le_disconnect¶

This function closes a client connection made by bluetooth_le_connect, or cancels it while it is still connecting. The disconnect is synchronous: the handle is retired by the call, together with every service, characteristic and descriptor handle discovered on it, and the callback set with bluetooth_set_callback_le_disconnected is not called for it.

Every operation still waiting on the connection (a discovery, a read, a write, a subscription, an RSSI or MTU request) is failed once with BluetoothError.Disconnected, and a connect still in progress calls its callback once with BluetoothError.ConnectionFailed.

The function returns BluetoothError.NotInitialized before bluetooth_initialize, and InvalidHandle for a handle that is not a live client connection: one already disconnected, dropped or failed, or a server connection, which ends when the central disconnects.


Syntax:

bluetooth_le_disconnect(connection)
Argument Type Description
connection Real The client connection handle to close.


Returns:

BluetoothError


Example:

if (bluetooth_le_connection_is_valid(connection))
{
    bluetooth_le_disconnect(connection);
}
connection = 0;
The above code closes the connection stored in connection if its handle is still valid, then clears the variable.

bluetooth_le_connection_is_valid¶

This function checks whether the given handle names a live client connection. A handle is valid from the moment bluetooth_le_connect returns it, while it is still connecting, until it is disconnected, drops or fails to connect.

Note

On Android this function also returns true for a server connection handle, which the other platforms report as not valid.


Syntax:

bluetooth_le_connection_is_valid(connection)
Argument Type Description
connection Real The connection handle to check.


Returns:

Boolean

true if the handle is a live client connection, otherwise false.


Example:

if (!bluetooth_le_connection_is_valid(connection))
{
    connection = 0;
}
The above code clears the instance variable connection when the handle it holds is no longer valid.

bluetooth_le_connection_is_connected¶

This function checks whether the given connection is currently connected. It returns false while the connection is still being made, after it has dropped, and for a handle that is not valid.

Note

On Android this function also returns true for a connected server connection handle.


Syntax:

bluetooth_le_connection_is_connected(connection)
Argument Type Description
connection Real The connection handle to check.


Returns:

Boolean

true if the connection is connected, otherwise false.


Example:

if (bluetooth_le_connection_is_connected(connection))
{
    bluetooth_le_characteristic_read(characteristic, on_read);
}
The above code reads a characteristic only when the connection stored in connection is connected.

bluetooth_le_connection_get_device¶

This function returns the handle of the device the given connection was made to, or 0 for a handle that is not a live client connection.

Note

On Android this function also returns the central's device handle for a server connection.


Syntax:

bluetooth_le_connection_get_device(connection)
Argument Type Description
connection Real The connection handle.


Returns:

Real

The device handle, or 0 if the connection is not valid.


Example:

var _device = bluetooth_le_connection_get_device(connection);
show_debug_message($"Connected to {bluetooth_device_get_name(_device)}");
The above code gets the device of the connection stored in connection and writes its name to the output log.

bluetooth_le_connection_get_mtu¶

This function returns the ATT MTU (Maximum Transmission Unit) of a connected client connection. A notification or a write without response carries at most mtu - 3 bytes. The MTU is 23 until a larger one is negotiated, and the function returns 0 for a handle that is not a connected client connection.

Note

Windows and Apple negotiate the MTU themselves when the link opens, so the value is the negotiated one from the start. On Android the value changes when bluetooth_le_connection_request_mtu completes, or when the device or the system negotiates it.


Syntax:

bluetooth_le_connection_get_mtu(connection)
Argument Type Description
connection Real The client connection handle.


Returns:

Real

The ATT MTU (in bytes), or 0 if the connection is not connected.


Example:

var _max_write = bluetooth_le_connection_get_mtu(connection) - 3;
show_debug_message($"A write without response can carry {_max_write} bytes");
The above code works out the largest write without response the connection can carry and writes it to the output log.

bluetooth_le_connection_request_mtu¶

This function asks for an ATT MTU of the given number of bytes on a connected client connection. The callback is called once with the MTU now in effect, which the device may have lowered. bluetooth_feature_is_supported with BluetoothFeature.LeMtuRequest says whether the platform really negotiates the size you ask for.

If the request cannot start, the function returns a BluetoothError other than Ok: NotInitialized, InvalidHandle for a handle that is not a client connection, InvalidArgument for an mtu outside 23-517, or Disconnected while the connection is not connected. The callback is then never called, and the reason is in bluetooth_last_error_message.

Note

Only Android negotiates the MTU on request. Windows and Apple negotiate it themselves when the link opens: the callback is called at once with BluetoothError.Ok and that MTU.

This function operates asynchronously, which means that it does not immediately return the requested result. Instead, upon completion of the task, it will trigger the Callback.


Syntax:

bluetooth_le_connection_request_mtu(connection, mtu, callback)
Argument Type Description
connection Real The client connection handle.
mtu Real The ATT MTU to ask for (23-517, in bytes).
callback Function The function to call once with the MTU in effect.


Returns:

BluetoothError


Triggers:

Callback

Called once, when the MTU request completes or fails.

Key Type Description
error_code BluetoothError BluetoothError.Ok if the request completed, otherwise the reason it failed.
message String A description of the failure, or an empty string on success.
connection Real The connection handle.
mtu Real The ATT MTU now in effect (in bytes), or 0 on failure.


Example:

var _error = bluetooth_le_connection_request_mtu(connection, 247, function(_error_code, _message, _connection, _mtu)
{
    if (_error_code != BluetoothError.Ok)
    {
        show_debug_message($"MTU request failed: {_message}");
        return;
    }
    show_debug_message($"MTU is now {_mtu} bytes");
});

if (_error != BluetoothError.Ok)
{
    show_debug_message($"MTU request did not start: {bluetooth_last_error_message()}");
}
The above code asks for an MTU of 247 bytes on the connection stored in connection. The callback writes the MTU in effect to the output log, or the reason the request failed. If the request could not start, the reason is read with bluetooth_last_error_message.

bluetooth_le_connection_read_rssi¶

This function reads the signal strength (RSSI) of a connected client connection. The callback is called once with the value in dBm. bluetooth_feature_is_supported with BluetoothFeature.LeReadRssi says whether the platform can do it.

If the read cannot start, the function returns a BluetoothError other than Ok: NotInitialized, InvalidHandle for a handle that is not a client connection, NotSupported where the platform cannot read the RSSI of a connection, or Disconnected while the connection is not connected. The callback is then never called, and the reason is in bluetooth_last_error_message.

Note

Windows has no API to read the RSSI of a connection and always returns NotSupported. Android, macOS and iOS support it.

This function operates asynchronously, which means that it does not immediately return the requested result. Instead, upon completion of the task, it will trigger the Callback.


Syntax:

bluetooth_le_connection_read_rssi(connection, callback)
Argument Type Description
connection Real The client connection handle.
callback Function The function to call once with the signal strength.


Returns:

BluetoothError


Triggers:

Callback

Called once, when the RSSI has been read or the read failed.

Key Type Description
error_code BluetoothError BluetoothError.Ok if the RSSI was read, otherwise the reason it was not.
message String A description of the failure, or an empty string on success.
connection Real The connection handle.
rssi Real The signal strength (in dBm), or 0 on failure.


Example:

if (bluetooth_feature_is_supported(BluetoothFeature.LeReadRssi))
{
    var _error = bluetooth_le_connection_read_rssi(connection, function(_error_code, _message, _connection, _rssi)
    {
        if (_error_code != BluetoothError.Ok)
        {
            show_debug_message($"RSSI read failed: {_message}");
            return;
        }
        signal_strength = _rssi;
    });

    if (_error != BluetoothError.Ok)
    {
        show_debug_message($"RSSI read did not start: {bluetooth_last_error_message()}");
    }
}
The above code first checks that the platform can read the RSSI of a connection. It then reads the RSSI of the connection stored in connection, and the callback stores the value in the instance variable signal_strength, or writes the reason to the output log if the read failed.

bluetooth_le_connection_request_priority¶

This function asks the platform to run a client connection at the given priority, trading speed against power. The request is synchronous: BluetoothError.Ok means the request was made, and no platform reports what the link settled on. bluetooth_feature_is_supported with BluetoothFeature.LeConnectionPriority says whether the platform can do it.

The function returns a BluetoothError other than Ok when the request is not made: NotInitialized, InvalidHandle for a handle that is not a client connection, InvalidArgument for a value that is not a BluetoothLeConnectionPriority, NotSupported where the platform cannot set it, Disconnected while the connection is not connected, or OperationFailed when the system refused the request. The reason is in bluetooth_last_error_message.

Note

Android supports connection priority. Windows 11 sets the preferred connection parameters, held for the life of the link; Windows 10 returns NotSupported. Apple always returns NotSupported.


Syntax:

bluetooth_le_connection_request_priority(connection, priority)
Argument Type Description
connection Real The client connection handle.
priority BluetoothLeConnectionPriority The priority to ask for.


Returns:

BluetoothError


Example:

if (bluetooth_feature_is_supported(BluetoothFeature.LeConnectionPriority))
{
    var _error = bluetooth_le_connection_request_priority(connection, BluetoothLeConnectionPriority.High);
    if (_error != BluetoothError.Ok)
    {
        show_debug_message($"Priority request failed: {bluetooth_last_error_message()}");
    }
}
The above code asks for the high connection priority on the connection stored in connection when the platform supports it, and writes the reason to the output log if the request was not made.

bluetooth_le_services_discover¶

This function starts discovering the GATT services of the device on a connected client connection. When the callback reports BluetoothError.Ok, the services are listed by bluetooth_le_service_get_count and bluetooth_le_service_get_at.

The services, characteristics and descriptors of a device are addressed by handles, not by UUID, so two attributes that share a UUID get their own handles. Discovery goes one level at a time: services first, then bluetooth_le_characteristics_discover on each service you need, then bluetooth_le_descriptors_discover on each characteristic whose descriptors you need. The getters list each level in the order discovery found it. Running discovery again keeps the handles of the attributes that are still there. Every handle discovered on a connection is retired when the connection ends.

If discovery cannot start, the function returns a BluetoothError other than Ok: NotInitialized, InvalidHandle for a handle that is not a client connection, or Disconnected while the connection is not connected (OperationFailed on Apple). The callback is then never called, and the reason is in bluetooth_last_error_message. A connection that ends while discovery is running fails it with Disconnected.

Note

Android downloads the whole GATT database in this one step, so on Android the characteristic and descriptor discoveries that follow complete at once.

bluetooth_le_characteristic_read¶

This function starts reading the value of the given characteristic. The callback is called once with a value handle and the size of the value in bytes. Copy the bytes into a buffer with bluetooth_value_fetch, which also frees the value; if you do not need them, free the value with bluetooth_value_release. A value that is neither fetched nor released is dropped 30 seconds after its callback was queued, and at most 256 LE read and notification values are held at a time (the oldest is dropped past that), so fetch or release each value in the callback. A successful read of 0 bytes still delivers a value handle; a failed read delivers 0 and needs nothing freed.

If the read cannot start, the function returns a BluetoothError other than Ok: NotInitialized, InvalidHandle for a handle that is not a discovered characteristic, or Disconnected while the connection is not connected (OperationFailed on Apple). The callback is then never called, and the reason is in bluetooth_last_error_message. A device that refuses the read reports NotPermitted, or InsufficientSecurity when it needs pairing or encryption first, through the callback.

Note

Apple reports reads and notifications through one system call, so on a subscribed characteristic a notification that arrives while the read is in flight can be what the read returns.

This function operates asynchronously, which means that it does not immediately return the requested result. Instead, upon completion of the task, it will trigger the Callback.


Syntax:

bluetooth_le_characteristic_read(characteristic, callback)
Argument Type Description
characteristic Real The characteristic handle.
callback Function The function to call once with the value read.


Returns:

BluetoothError


Triggers:

Callback

Called once, when the read completes or fails.

Key Type Description
error_code BluetoothError BluetoothError.Ok if the value was read, otherwise the reason it was not.
message String A description of the failure, or an empty string on success.
characteristic Real The characteristic handle.
value Real The value handle holding the bytes read, to pass to bluetooth_value_fetch, or 0 on failure.
size Real The size of the value (in bytes), or 0 on failure.


Example:

{

    {
        show_debug_message($"Read failed: {_message}");
        return;

    var _copied = bluetooth_value_fetch(_value, _buffer, 0);

});

    show_debug_message($"Read did not start: {bluetooth_last_error_message()}");
}
The above code reads the characteristic stored in battery_level. If the read failed, or could not start, the reason is written to the output log instead.

bluetooth_le_characteristic_write¶

This function writes the given number of bytes from the given buffer, starting at the given offset, to a characteristic. The bytes are copied when you call the function, so you can change or delete the buffer as soon as it returns. The callback is called once: for BluetoothLeWriteType.WithResponse when the device has confirmed or refused the write, and for WithoutResponse when the platform has taken the bytes.

A write without response carries at most mtu - 3 bytes, where mtu is the value of bluetooth_le_connection_get_mtu, so you should keep such writes within that length on every platform.

If the write cannot start, the function returns a BluetoothError other than Ok: NotInitialized, InvalidHandle for a handle that is not a discovered characteristic, InvalidArgument for a write_type that is not a BluetoothLeWriteType or an offset and size outside the buffer, NotSupported for a write without response on a characteristic without the WriteWithoutResponse property, Busy while 64 writes without response wait to be sent on the connection, or Disconnected while the connection is not connected (OperationFailed on Apple). The callback is then never called, and the reason is in bluetooth_last_error_message. A device that refuses the write reports NotPermitted, or InsufficientSecurity when it needs pairing or encryption first, through the callback.

Note

On Apple a write without response is also InvalidArgument past the link's maximum write length.

This function operates asynchronously, which means that it does not immediately return the requested result. Instead, upon completion of the task, it will trigger the Callback.

bluetooth_set_callback_le_disconnected¶

This function sets the function that is called when an established client connection ends without bluetooth_le_disconnect: the device dropped it, the link failed or the radio was turned off. When it is called, the connection handle has already been retired, together with every service, characteristic and descriptor handle discovered on it, and every operation that was waiting on the connection has been failed with BluetoothError.Disconnected. A disconnect you asked for with bluetooth_le_disconnect does not call it, and neither does a connect that fails, which reports through its own callback.

Setting a new function replaces the previous one. The function stays set across bluetooth_shutdown and bluetooth_initialize. The function always returns true.

This function operates asynchronously, which means that it does not immediately return the requested result. Instead, upon completion of the task, it will trigger the Callback.

bluetooth_set_callback_le_disconnected(function(_error_code, _message, _connection)

The above code sets the function that is called when a client connection drops. When the connection that dropped is the one stored in connection, it writes the reason to the output log and clears the variable.

bluetooth_set_callback_le_characteristic_value_changed¶

This function sets the function that is called for every notification or indication a subscribed characteristic sends (see bluetooth_le_characteristic_subscribe). The callback receives a value handle and the size of the value in bytes: copy the bytes into a buffer with bluetooth_value_fetch, which also frees the value, or free it with bluetooth_value_release if you do not need them. A value that is neither fetched nor released is dropped 30 seconds after its callback was queued, and at most 256 LE read and notification values are held at a time (the oldest is dropped past that), so fetch or release each value in the callback.

Only characteristics discovered with bluetooth_le_characteristics_discover on the connection are reported. While no function is set, notifications are dropped and no value is kept for them.

Setting a new function replaces the previous one. The function stays set across bluetooth_shutdown and bluetooth_initialize. The function always returns true.

This function operates asynchronously, which means that it does not immediately return the requested result. Instead, upon completion of the task, it will trigger the Callback.


Syntax:

bluetooth_set_callback_le_characteristic_value_changed(callback)
Argument Type Description
callback Function The function to call for every notification or indication.


Returns:

Boolean

Always true.


Triggers:

Callback

Called once for every notification or indication a subscribed characteristic sends.

Key Type Description
characteristic Real The handle of the characteristic that sent the value.
connection Real The handle of the client connection the value arrived on.
value Real The value handle holding the bytes, to pass to bluetooth_value_fetch.
size Real The size of the value (in bytes).


Example:

notify_buffer = buffer_create(512, buffer_fixed, 1);

bluetooth_set_callback_le_characteristic_value_changed(function(_characteristic, _connection, _value, _size)
{
    if (_characteristic != measurement || _size < 2)
    {
        bluetooth_value_release(_value);
        return;
    }
    bluetooth_value_fetch(_value, notify_buffer, 0);
    var _flags = buffer_peek(notify_buffer, 0, buffer_u8);
    var _rate = ((_flags & 1) != 0) ? buffer_peek(notify_buffer, 1, buffer_u16) : buffer_peek(notify_buffer, 1, buffer_u8);
    show_debug_message($"Heart rate: {_rate} bpm");
});
The above code creates a 512-byte buffer, large enough for any characteristic value, and sets the function that is called for every notification. A value from any characteristic other than the one stored in measurement, or one too short to read, is freed with bluetooth_value_release. Otherwise the bytes are copied into the buffer with bluetooth_value_fetch and the heart rate is read from them, as an 8-bit or a 16-bit value depending on the first bit of the flags byte, and written to the output log.

BluetoothLeScanFilter¶

This struct is one filter for bluetooth_le_scan_start. A device matches when every field the filter sets matches what the device has advertised, merged over every advertisement and scan response it has sent since it entered the device cache (see BluetoothLeAdvertisement). A field left undefined is not checked, and a filter must set at least one field, otherwise the scan start is InvalidArgument.

Note

On Android, while a filtered scan runs, the Bluetooth stack delivers only the advertisements that carry a field one of the filters sets, so a found device's other advertisements do not update its signal strength or advertisement until the scan stops.

This struct is referenced by the following functions:

  • bluetooth_le_scan_start


Member Type Description
service_uuid String The service UUID the device must advertise, in 4-digit, 8-digit or 36-character form.
name String The advertised local name the device must have, matched exactly.
company_id Real The Bluetooth SIG company identifier (0-65535) the device must advertise manufacturer data for.
