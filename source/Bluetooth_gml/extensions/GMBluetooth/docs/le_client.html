LE Client¶

The functions to scan for Bluetooth LE devices, connect to them as a GATT client, and discover, read, write and subscribe to their services, characteristics and descriptors.

Each call that starts something takes the functions to call for its events and keeps them until it ends: a scan its on_found, on_updated and on_stopped, a connection its on_disconnected, a subscription its on_value. The event that ends it, on_stopped or on_disconnected, is the last one, and it is not called when you end it yourself with bluetooth_le_scan_stop or bluetooth_le_disconnect. Starting something that is already running returns BluetoothError.Busy.

A connection, and every service, characteristic and descriptor on it, is addressed by an opaque handle, so two attributes that share a UUID get their own handles. bluetooth_le_services_discover discovers the services of a connected device, and with a BluetoothLeDiscoverOptions their characteristics and descriptors too; the getters, such as bluetooth_le_service_get_count and bluetooth_le_service_get_at, list each level in the order discovery found it, and the find functions, such as bluetooth_le_service_find, look one up by UUID. Every handle discovered on a connection is retired when the connection ends.

The bytes of a read or a notification arrive as a value handle and a size, and are copied into a buffer with bluetooth_value_fetch or bluetooth_value_to_buffer. A call that fails before it starts returns a BluetoothError (or 0 for bluetooth_le_connect and the find functions) and never calls its callbacks; bluetooth_last_error_message gives the reason.

bluetooth_le_scan_start¶

This function starts scanning for Bluetooth LE devices. Every device the scan sees enters the shared device cache, and the scan calls its own callbacks for it: on_found the first time this scan sees the device, also when an earlier scan already put it in the cache, and on_updated for each later advertisement in the same scan, at most once per update_interval_ms per device. Each advertisement updates the device's name, signal strength and advertisement, which bluetooth_device_get_name, bluetooth_device_get_rssi and bluetooth_device_get_advertisement return.

The scan keeps its callbacks until it ends. When it ends without bluetooth_le_scan_stop, for example with BluetoothError.BluetoothDisabled when the radio is turned off, on_stopped is called once with the reason; a scan you stop yourself calls nothing. Only an LE scan reports LE devices, and a device that enters the cache in another way, such as through bluetooth_device_from_id, calls no scan callback.

The given settings is a BluetoothLeScanSettings, or undefined for an active scan in BluetoothLeScanMode.LowLatency mode with an update interval of 1000 milliseconds. The given filters array holds BluetoothLeScanFilter structs; undefined or an empty array reports every device. Otherwise the scan reports a device once its advertisement record, merged over every advertisement and scan response it has sent, matches any one of the filters.

Only one LE scan runs at a time: a start while a scan is running returns BluetoothError.Busy, so stop the scan first to change its settings, filters or callbacks. While the Bluetooth state is still BluetoothState.Unknown the scan starts once the radio is ready.

If the scan cannot start, the function returns a BluetoothError other than Ok: NotInitialized, InvalidArgument for a bad setting or filter (a filter that sets no field, a malformed UUID, a company_id outside 0-65535, data without its key, a mask of another length than its data, an update_interval_ms outside 0-60000), Busy while a scan runs, PermissionDenied when the Bluetooth permission is missing or was refused, BluetoothDisabled when the radio is off or resetting, NotSupported when there is no Bluetooth LE hardware, or OperationFailed when the platform refused to start. The reason is in bluetooth_last_error_code and bluetooth_last_error_message, and no scan callback is called.

Note

Android filters in the Bluetooth stack and allows 5 scan starts per 30 seconds: a sixth starts but finds nothing. It also pauses unfiltered scans while the screen is off, and on Android 6 to 11 a scan returns PermissionDenied while the system Location setting is off. With the manifest's neverForLocation flag it also leaves out some beacon advertisements. Only Android uses the mode of the settings (BluetoothFeature.LeScanMode).

Note

Apple and Android always scan actively; only Windows can scan passively (BluetoothFeature.LePassiveScan). iOS needs every filter to set service_uuid to scan in the background, and never reports iBeacon advertisements.

This function operates asynchronously, which means that it does not immediately return the requested result. Instead, upon completion of the task, it will trigger the Callback.


Syntax:

bluetooth_le_scan_start(settings=undefined, filters=undefined, on_found, on_updated=undefined, on_stopped=undefined)
Argument Type Description
settings BluetoothLeScanSettings How the scan runs, or undefined for the defaults.
filters Array of BluetoothLeScanFilter The filters a device must match one of, or undefined or an empty array for every device.
on_found Function The function to call the first time this scan sees a device.
on_updated Function The function to call for a later advertisement of a device this scan has already reported, or undefined.
on_stopped Function The function to call when the scan ends without bluetooth_le_scan_stop, or undefined.


Returns:

BluetoothError

BluetoothError.Ok if the scan started, otherwise the reason it did not.


Triggers:

Callback - on_found

Called once for each device, the first time this scan sees it.

Key Type Description
device Real The handle of the device.


Callback - on_updated

Called for a later advertisement of a device this scan has already reported, at most once per update_interval_ms per device.

Key Type Description
device Real The handle of the device.


Callback - on_stopped

Called once, when the scan ends without bluetooth_le_scan_stop. It is the last callback of the scan.

Key Type Description
error_code BluetoothError The reason the scan ended, such as BluetoothError.BluetoothDisabled when the radio was turned off.
message String A description of why the scan ended.


Example:

var _settings = new BluetoothLeScanSettings();
_settings.update_interval_ms = 2000;

var _filter = new BluetoothLeScanFilter();
_filter.service_uuid = "180d";

var _error = bluetooth_le_scan_start(_settings, [_filter],
    function(_device)
    {
        show_debug_message($"Found {bluetooth_device_get_name(_device)}");
        array_push(devices, _device);
    },
    function(_device)
    {
        var _rssi = bluetooth_device_get_rssi(_device);
        if (_rssi != undefined)
        {
            show_debug_message($"{bluetooth_device_get_name(_device)}: {_rssi} dBm");
        }
    },
    function(_error_code, _message)
    {
        show_debug_message($"Scan ended: {_message}");
    });

if (_error != BluetoothError.Ok)
{
    show_debug_message($"Scan did not start: {bluetooth_last_error_message()}");
}
The above code creates a BluetoothLeScanSettings that reports a device's later advertisements at most every 2 seconds, and a BluetoothLeScanFilter that matches devices advertising the Heart Rate service (0x180D). It then starts the scan with three callbacks: on_found writes the name of each new device to the output log and adds its handle to the instance's devices array, on_updated writes the device's latest signal strength when it has one, and on_stopped writes why the scan ended on its own. If the scan could not start, the reason is read with bluetooth_last_error_message.

bluetooth_le_scan_stop¶

This function stops the running Bluetooth LE scan. The scan's on_stopped callback is not called for a stop you ask for, and the scan calls none of its callbacks after this function returns. A stop while no scan is running returns BluetoothError.Ok and does nothing.

The function returns BluetoothError.NotInitialized before bluetooth_initialize, and on Windows OperationFailed when the platform could not stop its scanner; the scan counts as stopped in that case too. The reason is in bluetooth_last_error_message.


Syntax:

bluetooth_le_scan_stop()


Returns:

BluetoothError

BluetoothError.Ok if the scan is stopped or none was running, otherwise the reason.


Example:

if (bluetooth_le_scan_is_running())
{
    bluetooth_le_scan_stop();
}
The above code stops the Bluetooth LE scan if one is running.

bluetooth_le_connected_devices_query¶

This function lists the Bluetooth LE devices that are connected to this system, by this game or by another app, and that expose one of the given services, without a scan. The callback is called once with an array of device handles. A device that is not in the device cache yet enters it without calling any scan callback. You can pass a handle from the list to bluetooth_le_connect.

Every UUID in the given service_uuids array is checked first. If the query cannot start, the function returns a BluetoothError other than Ok: NotInitialized, InvalidArgument for an empty array or a malformed UUID, PermissionDenied, BluetoothDisabled or NotSupported as for bluetooth_le_scan_start, and the callback is never called. The reason is in bluetooth_last_error_message.

Note

Android and Windows cannot filter by service, so they list every connected LE device. Apple lists only the devices that expose one of the given services, and the radio must already be on (BluetoothDisabled otherwise).

This function operates asynchronously, which means that it does not immediately return the requested result. Instead, upon completion of the task, it will trigger the Callback.


Syntax:

bluetooth_le_connected_devices_query(service_uuids, callback)
Argument Type Description
service_uuids Array of String The service UUIDs a device must expose one of; it must not be empty.
callback Function The function to call once with the list of connected devices.


Returns:

BluetoothError

BluetoothError.Ok if the query started, otherwise the reason it did not.


Triggers:

Callback

Called once, with the connected devices or the reason the query failed.

Key Type Description
error_code BluetoothError BluetoothError.Ok if the query succeeded, otherwise the reason it failed.
message String A description of the failure, or an empty string on success.
devices Array of Real The handles of the connected devices, empty on failure.


Example:

var _error = bluetooth_le_connected_devices_query(["180d"], function(_error_code, _message, _devices)
{
    if (_error_code != BluetoothError.Ok)
    {
        show_debug_message($"Query failed: {_message}");
        return;
    }
    for (var _i = 0; _i < array_length(_devices); _i++)
    {
        show_debug_message($"Connected: {bluetooth_device_get_name(_devices[_i])}");
    }
});

if (_error != BluetoothError.Ok)
{
    show_debug_message($"Query did not start: {bluetooth_last_error_message()}");
}
The above code asks for the LE devices connected to the system that expose the Heart Rate service. The callback writes the reason to the output log if the query failed, otherwise the name of each device it found. If the query could not start at all, the reason is read with bluetooth_last_error_message and the callback is never called.

bluetooth_le_connect¶

This function starts a GATT connection to the given Bluetooth LE device, which must have been found by a scan, listed by bluetooth_le_connected_devices_query or looked up with bluetooth_device_from_id. It returns a connection handle straight away, before the device has answered, and callback is called once when the connection is made or fails.

The function returns 0 when the connect could not be started, and the reason is then in bluetooth_last_error_code and bluetooth_last_error_message: NotInitialized, InvalidHandle for a device handle that is not valid, InvalidArgument for a Classic device, one with no usable address or options that are not valid, PermissionDenied, BluetoothDisabled, NotSupported, or Busy when the device already has a connection. In that case no callback is ever called.

The given options is a BluetoothConnectOptions, or undefined for the defaults. A device that does not answer within its timeout_ms, 15 seconds by default, fails with BluetoothError.Timeout, and one that refuses or whose link fails with ConnectionFailed. You can cancel a connect that is still in progress by passing the returned handle to bluetooth_le_disconnect, and callback is then called once with BluetoothError.ConnectionFailed. bluetooth_shutdown fails a connect still in progress with NotInitialized, and the radio turning off fails it with BluetoothDisabled. A connect that fails retires its handle.

Once the connection is open, on_disconnected is called once if the link ends without bluetooth_le_disconnect: the device dropped it, the link failed, or the radio was turned off (BluetoothError.BluetoothDisabled). When it is called, the connection handle has already been retired, together with every service, characteristic and descriptor handle discovered on it, and every operation that was waiting on the connection has been failed with BluetoothError.Disconnected. A disconnect you ask for does not call it, and neither does a connect that fails, which reports through callback.

Note

A device can only have one client connection at a time, whether it is still connecting or already connected.

Note

On Apple the connect also returns 0 with NotFound for a device that CoreBluetooth no longer knows (scan for it again), and with PermissionDenied until bluetooth_permission_request has been answered.

This function operates asynchronously, which means that it does not immediately return the requested result. Instead, upon completion of the task, it will trigger the Callback.


Syntax:

bluetooth_le_connect(device, options=undefined, on_disconnected, callback)
Argument Type Description
device Real The handle of the LE device to connect to.
options BluetoothConnectOptions How the connect runs, or undefined for the defaults.
on_disconnected Function The function to call once if the open connection ends without bluetooth_le_disconnect.
callback Function The function to call once the connection is made or fails.


Returns:

Real

The new connection handle, or 0 if the connect did not start.


Triggers:

Callback - on_disconnected

Called once, when the open connection ends without bluetooth_le_disconnect. It is the last callback of the connection.

Key Type Description
error_code BluetoothError The reason the connection ended, such as BluetoothError.Disconnected when the device dropped it or BluetoothError.BluetoothDisabled when the radio was turned off.
message String A description of why the connection ended.
connection Real The handle of the connection that ended, which is no longer valid.


Callback - callback

Called once, when the connection is made, fails or is cancelled.

Key Type Description
error_code BluetoothError BluetoothError.Ok if the device is connected, otherwise the reason it is not.
message String A description of the failure, or an empty string on success.
connection Real The connection handle that bluetooth_le_connect returned.
device Real The handle of the device.


Example:

var _options = new BluetoothConnectOptions();
_options.timeout_ms = 10000;

connection = bluetooth_le_connect(device, _options,
    function(_error_code, _message, _connection)
    {
        if (_connection != connection) return;
        show_debug_message($"Connection lost: {_message}");
        connection = 0;
    },
    function(_error_code, _message, _connection, _device)
    {
        if (_connection != connection) return;
        if (_error_code != BluetoothError.Ok)
        {
            show_debug_message($"Connect failed: {_message}");
            connection = 0;
            return;
        }
        show_debug_message("Connected, discovering services");
        bluetooth_le_services_discover(_connection, undefined, on_services);
    });

if (connection == 0)
{
    show_debug_message($"Connect did not start: {bluetooth_last_error_message()}");
}
The above code connects to the device stored in the instance's device variable, giving up after 10 seconds, and keeps the returned handle in connection. Both callbacks first check that the connection they report is still the one stored in connection, so a callback for an older connection the instance has since replaced is ignored. When the connect fails, or the open connection is lost later, the reason is written to the output log and the handle is cleared; on success the services of the device are discovered next with bluetooth_le_services_discover, which calls the instance's on_services method. If the connect could not be started at all, the returned handle is 0 and the reason is read with bluetooth_last_error_message.

bluetooth_le_disconnect¶

This function closes a client connection made by bluetooth_le_connect, or cancels it while it is still connecting. The disconnect is synchronous: the handle is retired by the call, together with every service, characteristic and descriptor handle discovered on it and every subscription on it, and the connection's on_disconnected callback is not called.

Every operation still waiting on the connection (a discovery, a read, a write, a subscription, an RSSI or MTU request) is failed once with BluetoothError.Disconnected, and a connect still in progress calls its callback once with BluetoothError.ConnectionFailed.

The function returns BluetoothError.NotInitialized before bluetooth_initialize, and InvalidHandle for a handle that is not a live client connection: one already disconnected, dropped or failed, or a server connection, which ends when the central disconnects.


Syntax:

bluetooth_le_disconnect(connection)
Argument Type Description
connection Real The client connection handle to close.


Returns:

BluetoothError

BluetoothError.Ok if the connection was closed or the connect cancelled, otherwise the reason.


Example:

if (bluetooth_le_connection_is_valid(connection))
{
    bluetooth_le_disconnect(connection);
}
connection = 0;
The above code closes the connection stored in connection if its handle is still valid, then clears the variable.

bluetooth_le_connection_is_valid¶

This function checks whether the given handle names a live LE connection. A client connection is valid from the moment bluetooth_le_connect returns it, while it is still connecting, until it is disconnected, drops or fails to connect. A server connection, which the LE server's on_connected callback reports, is valid until its central disconnects or the server stops.


Syntax:

bluetooth_le_connection_is_valid(connection)
Argument Type Description
connection Real The connection handle to check.


Returns:

Boolean

true if the handle is a live client or server connection, otherwise false.


Example:

if (!bluetooth_le_connection_is_valid(connection))
{
    connection = 0;
}
The above code clears the instance variable connection when the handle it holds is no longer valid.

bluetooth_le_connection_get_mtu¶

This function returns the ATT MTU (Maximum Transmission Unit) of a connected client or server connection. A notification or a write without response carries at most mtu - 3 bytes. The MTU is 23 until a larger one is negotiated, and the function returns 0 for a handle that is not a connected LE connection.

For a server connection it is the MTU of the central's link, which tells you how much of a value bluetooth_le_server_notify_value can send to that central in one notification.

Note

Windows and Apple negotiate the MTU of a client connection themselves when the link opens, so the value is the negotiated one from the start. On Android the value changes when bluetooth_le_connection_request_mtu completes, or when the device or the system negotiates it, and a server connection reports 23 until the central negotiates a larger MTU.


Syntax:

bluetooth_le_connection_get_mtu(connection)
Argument Type Description
connection Real The client or server connection handle.


Returns:

Real

The ATT MTU (in bytes), or 0 if the connection is not connected.


Example:

var _max_write = bluetooth_le_connection_get_mtu(connection) - 3;
show_debug_message($"A write without response can carry {_max_write} bytes");
The above code works out the largest write without response the connection can carry and writes it to the output log.

bluetooth_le_connection_request_mtu¶

This function asks for an ATT MTU of the given number of bytes on a connected client connection. The callback is called once with the MTU now in effect, which the device may have lowered. bluetooth_feature_is_supported with BluetoothFeature.LeMtuRequest says whether the platform really negotiates the size you ask for.

If the request cannot start, the function returns a BluetoothError other than Ok: NotInitialized, InvalidHandle for a handle that is not a client connection, InvalidArgument for an mtu outside 23-517, or Disconnected while the connection is not connected. The callback is then never called, and the reason is in bluetooth_last_error_message.

Note

Only Android negotiates the MTU on request. Windows and Apple negotiate it themselves when the link opens: the callback is called at once with BluetoothError.Ok and that MTU.

This function operates asynchronously, which means that it does not immediately return the requested result. Instead, upon completion of the task, it will trigger the Callback.


Syntax:

bluetooth_le_connection_request_mtu(connection, mtu, callback)
Argument Type Description
connection Real The client connection handle.
mtu Real The ATT MTU to ask for (23-517, in bytes).
callback Function The function to call once with the MTU in effect.


Returns:

BluetoothError

BluetoothError.Ok if the request started, otherwise the reason it did not.


Triggers:

Callback

Called once, when the MTU request completes or fails.

Key Type Description
error_code BluetoothError BluetoothError.Ok if the request completed, otherwise the reason it failed.
message String A description of the failure, or an empty string on success.
connection Real The connection handle.
mtu Real The ATT MTU now in effect (in bytes), or 0 on failure.


Example:

var _error = bluetooth_le_connection_request_mtu(connection, 247, function(_error_code, _message, _connection, _mtu)
{
    if (_error_code != BluetoothError.Ok)
    {
        show_debug_message($"MTU request failed: {_message}");
        return;
    }
    show_debug_message($"MTU is now {_mtu} bytes");
});

if (_error != BluetoothError.Ok)
{
    show_debug_message($"MTU request did not start: {bluetooth_last_error_message()}");
}
The above code asks for an MTU of 247 bytes on the connection stored in connection. The callback writes the MTU in effect to the output log, or the reason the request failed. If the request could not start, the reason is read with bluetooth_last_error_message.

bluetooth_le_connection_read_rssi¶

This function reads the signal strength (RSSI) of a connected client connection. The callback is called once with the value in dBm. bluetooth_feature_is_supported with BluetoothFeature.LeReadRssi says whether the platform can do it.

bluetooth_le_services_discover¶

This function starts discovering the GATT services of the device on a connected client connection. When the callback reports BluetoothError.Ok, the services are listed by bluetooth_le_service_get_count and bluetooth_le_service_get_at, and bluetooth_le_service_find looks one up by UUID.

The services, characteristics and descriptors of a device are addressed by handles, not by UUID, so two attributes that share a UUID get their own handles. Without options, discovery finds the services only, and you go one level at a time: bluetooth_le_characteristics_discover on each service you need, then bluetooth_le_descriptors_discover on each characteristic whose descriptors you need. With a BluetoothLeDiscoverOptions, the one callback is called after every level the options ask for has been discovered, in the services its service_uuids names (every service when it is undefined); the first failure is the callback's error, and what was found before it stays listed. Every service is listed either way.

The getters list each level in the order discovery found it. Running discovery again keeps the handles of the attributes that are still there and retires the handles of those that are gone, with every handle under them; a subscription on a characteristic that is gone ends. Every handle discovered on a connection is retired when the connection ends.

If discovery cannot start, the function returns a BluetoothError other than Ok: NotInitialized, InvalidHandle for a handle that is not a client connection, InvalidArgument for options that are not valid, or Disconnected while the connection is not connected. The callback is then never called, and the reason is in bluetooth_last_error_message. A connection that ends while discovery is running fails it with Disconnected.

Note

Android downloads the whole GATT database in this one step, so on Android the characteristic and descriptor discoveries that follow complete at once.

This function operates asynchronously, which means that it does not immediately return the requested result. Instead, upon completion of the task, it will trigger the Callback.


Syntax:

bluetooth_le_services_discover(connection, options=undefined, callback)
Argument Type Description
connection Real The client connection handle.
options BluetoothLeDiscoverOptions How deep discovery goes, or undefined for the services only.
callback Function The function to call once discovery completes or fails.


Returns:

BluetoothError

BluetoothError.Ok if discovery started, otherwise the reason it did not.


Triggers:

Callback

Called once, when every level the options ask for has been discovered, or discovery fails.

Key Type Description
error_code BluetoothError BluetoothError.Ok if everything asked for was discovered, otherwise the first failure.
message String A description of the failure, or an empty string on success.
connection Real The connection handle.


Example:

var _options = new BluetoothLeDiscoverOptions();
_options.service_uuids = ["0000180d-0000-1000-8000-00805f9b34fb"];
_options.characteristics = true;

var _error = bluetooth_le_services_discover(connection, _options, function(_error_code, _message, _connection)
{
    if (_connection != connection) return;
    if (_error_code != BluetoothError.Ok)
    {
        show_debug_message($"Discovery failed: {_message}");
        return;
    }

    var _service = bluetooth_le_service_find(_connection, "180d");
    measurement = bluetooth_le_characteristic_find(_service, "2a37");
    if (measurement == 0)
    {
        show_debug_message($"No heart rate measurement: {bluetooth_last_error_message()}");
    }
});

if (_error != BluetoothError.Ok)
{
    show_debug_message($"Discovery did not start: {bluetooth_last_error_message()}");
}
The above code discovers the services of the device on the connection stored in connection, and the characteristics of its Heart Rate service, in one step. On success the callback finds the Heart Rate service with bluetooth_le_service_find and its Heart Rate Measurement characteristic (0x2A37) with bluetooth_le_characteristic_find, and keeps the characteristic's handle in the instance variable measurement. A find that matches nothing returns 0, and a find given 0 does too, so one check covers a device without the service or the characteristic. If discovery failed, or could not start at all, the reason is written to the output log instead.

bluetooth_le_characteristic_read¶

This function starts reading the value of the given characteristic. The callback is called once with a value handle and the size of the value in bytes. Copy the bytes into a buffer with bluetooth_value_fetch or bluetooth_value_to_buffer, which also free the value; if you do not need them, free the value with bluetooth_value_release. A value that is neither fetched nor released is dropped 30 seconds after its callback was queued, and at most 256 LE read and notification values are held at a time (the oldest is dropped past that), so fetch or release each value in the callback. A successful read of 0 bytes still delivers a value handle; a failed read delivers 0 and needs nothing freed.

If the read cannot start, the function returns a BluetoothError other than Ok: NotInitialized, InvalidHandle for a handle that is not a discovered characteristic, or Disconnected while the connection is not connected. The callback is then never called, and the reason is in bluetooth_last_error_message. A device that refuses the read reports NotPermitted, or InsufficientSecurity when it needs pairing or encryption first, through the callback.

Note

Apple reports reads and notifications through one system call, so on a subscribed characteristic a notification that arrives while the read is in flight can be what the read returns.

This function operates asynchronously, which means that it does not immediately return the requested result. Instead, upon completion of the task, it will trigger the Callback.


Syntax:

bluetooth_le_characteristic_read(characteristic, callback)
Argument Type Description
characteristic Real The characteristic handle.
callback Function The function to call once with the value read.


Returns:

BluetoothError

BluetoothError.Ok if the read started, otherwise the reason it did not.


Triggers:

Callback

Called once, when the read completes or fails.

Key Type Description
error_code BluetoothError BluetoothError.Ok if the value was read, otherwise the reason it was not.
message String A description of the failure, or an empty string on success.
characteristic Real The characteristic handle.
value Real The value handle holding the bytes read, to pass to bluetooth_value_fetch, or 0 on failure.
size Real The size of the value (in bytes), or 0 on failure.


Example:

var _error = bluetooth_le_characteristic_read(battery_level, function(_error_code, _message, _characteristic, _value, _size)
{
    if (_error_code != BluetoothError.Ok)
    {
        show_debug_message($"Read failed: {_message}");
        return;
    }
    if (_size < 1)
    {
        bluetooth_value_release(_value);
        return;
    }

    var _buffer = bluetooth_value_to_buffer(_value, _size);
    if (_buffer == -1)
    {
        show_debug_message($"Fetch failed: {bluetooth_last_error_message()}");
        return;
    }
    show_debug_message($"Battery level: {buffer_peek(_buffer, 0, buffer_u8)}%");
    buffer_delete(_buffer);
});

if (_error != BluetoothError.Ok)
{
    show_debug_message($"Read did not start: {bluetooth_last_error_message()}");
}
The above code reads the characteristic stored in battery_level. An empty value is released with bluetooth_value_release, since there is nothing to read. Otherwise the callback copies the value into a new buffer with bluetooth_value_to_buffer, which frees the value, and writes the first byte to the output log as the battery level before deleting the buffer. If the read failed, could not start, or the value could not be fetched, the reason is written to the output log instead.

bluetooth_le_characteristic_write¶

This function writes the given number of bytes from the given buffer, starting at the given offset, to a characteristic. The bytes are copied when you call the function, so you can change or delete the buffer as soon as it returns. The callback is called once: for BluetoothLeWriteType.WithResponse when the device has confirmed or refused the write, and for WithoutResponse when the platform has taken the bytes.

A write without response carries at most mtu - 3 bytes, where mtu is the value of bluetooth_le_connection_get_mtu, so you should keep such writes within that length on every platform.

If the write cannot start, the function returns a BluetoothError other than Ok: NotInitialized, InvalidHandle for a handle that is not a discovered characteristic, InvalidArgument for a write_type that is not a BluetoothLeWriteType or an offset and size outside the buffer, NotSupported for a write without response on a characteristic without the WriteWithoutResponse property, Busy while 64 writes without response wait to be sent on the connection, or Disconnected while the connection is not connected. The callback is then never called, and the reason is in bluetooth_last_error_message. A device that refuses the write reports NotPermitted, or InsufficientSecurity when it needs pairing or encryption first, through the callback.

Note

On Apple a write without response is also InvalidArgument past the link's maximum write length.

This function operates asynchronously, which means that it does not immediately return the requested result. Instead, upon completion of the task, it will trigger the Callback.

bluetooth_le_characteristic_subscribe¶

This function subscribes to the notifications or indications of the given characteristic, by writing its Client Characteristic Configuration descriptor (0x2902) on the device. callback is called once when the device has accepted or refused the subscription.

Every value the device then sends is passed to on_value, until the subscription ends: you call bluetooth_le_characteristic_unsubscribe, the connection ends, or a new discovery drops the characteristic. The callback receives a value handle and the size of the value in bytes: copy the bytes into a buffer with bluetooth_value_fetch, which also frees the value, or free it with bluetooth_value_release if you do not need them. A value that is neither fetched nor released is dropped 30 seconds after its callback was queued, and at most 256 LE read and notification values are held at a time (the oldest is dropped past that), so fetch or release each value in the callback.

If the subscription cannot start, the function returns a BluetoothError other than Ok: NotInitialized, InvalidHandle for a handle that is not a discovered characteristic, InvalidArgument for a mode that is not a BluetoothLeSubscribeMode, Busy while the characteristic is subscribed or subscribing, NotSupported for Notify on a characteristic without the Notify property or Indicate on one without the Indicate property, or Disconnected while the connection is not connected. No callback is then called, and the reason is in bluetooth_last_error_message.

Note

On Android a characteristic with no Client Characteristic Configuration descriptor is NotSupported from the call itself. Windows and Apple send the request to the device, and the callback reports the failure.

Note

On a characteristic with both the Notify and Indicate properties, Apple turns on notifications for either mode.

This function operates asynchronously, which means that it does not immediately return the requested result. Instead, upon completion of the task, it will trigger the Callback.

            return;
        }

        {
            show_debug_message($"Fetch failed: {bluetooth_last_error_message()}");
            return;
        }

        var _flags = buffer_peek(measurement_buffer, 0, buffer_u8);
        var _rate;
        if ((_flags & 1) != 0)
        {
            if (_size < 3) return;
            _rate = buffer_peek(measurement_buffer, 1, buffer_u16);
        }
        else
        {
            _rate = buffer_peek(measurement_buffer, 1, buffer_u8);
        }
        show_debug_message($"Heart rate: {_rate} bpm");
    },
    function(_error_code, _message, _characteristic)

        if (_error_code != BluetoothError.Ok)
        {
            show_debug_message($"Subscribe failed: {_message}");
        }

{

The above code creates a 512-byte buffer, large enough for any characteristic value, and subscribes to the notifications of the Heart Rate Measurement characteristic stored in measurement. The on_value callback releases, with bluetooth_value_release, a value that arrives for a connection other than the one stored in connection or that is too short to hold a heart rate. The first bit of the flags byte says whether the heart rate is an 8-bit or a 16-bit value; the 16-bit form needs 3 bytes, so a shorter value is skipped rather than read past its end. The heart rate is then written to the output log. The second callback reports a subscription the device refused, and if the subscription could not start, the reason is read with bluetooth_last_error_message.

BluetoothLeScanFilter¶

This struct is one filter for bluetooth_le_scan_start. You create it with new BluetoothLeScanFilter() and set the variables you want to filter on; every variable is optional, and one left undefined is not checked. A device matches when every variable the filter sets matches its advertisement record, merged over every advertisement and scan response it has sent (see BluetoothLeAdvertisement). A filter belongs to the scan it was passed to.

The data variables match the start of an advertised entry: an entry matches when its first bytes, as many as manufacturer_data or service_data holds, equal those bytes under the mask, compared bit by bit where the mask has a 1. A mask must have the same length as its data, and a mask left undefined compares every bit.

A filter must set at least one variable; manufacturer_data needs company_id, service_data needs service_data_uuid, and a mask needs its data. name and name_prefix can both be set, and must then both match. Anything else makes the scan start return InvalidArgument.

Note

On Android, while a filtered scan runs, the Bluetooth stack delivers only the advertisements that carry a field one of the filters sets, so a found device's other advertisements do not update its signal strength or advertisement until the scan stops.

This struct is referenced by the following functions:

  • bluetooth_le_scan_start

name String The advertised local name the device must have, matched exactly.
name_prefix String The text the device's advertised local name must start with.
company_id Real The Bluetooth SIG company identifier (0-65535) the device must advertise manufacturer data for.
manufacturer_data Array of Real The bytes the manufacturer data of company_id must start with, each entry a byte (0-255).
