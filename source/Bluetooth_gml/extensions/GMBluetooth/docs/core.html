Core¶

The functions to start and stop the extension, read the error of a failed call, check the platform's capabilities and permissions, turn the radio on, read the bytes that callbacks deliver, and follow the state of the local Bluetooth adapter.

Two of the value functions, bluetooth_value_to_buffer and bluetooth_value_append, are GML helpers written in the GMBluetooth_helpers script that ships with the extension, built on bluetooth_value_fetch.

bluetooth_initialize¶

This function starts the extension and its platform backend. You must call it before any other Bluetooth function: until it succeeds, every call that uses Bluetooth returns BluetoothError.NotInitialized.

The function returns true once the extension is running, and also when it is already running. It also returns true on a device that has no Bluetooth hardware: the extension then reports BluetoothState.Unsupported, bluetooth_feature_is_supported returns false and every Bluetooth call returns BluetoothError.NotSupported.

If the backend cannot be started, the function returns false and the reason is in bluetooth_last_error_code and bluetooth_last_error_message, normally BluetoothError.OperationFailed. The extension is then not initialised, so bluetooth_is_initialized returns false and you can call this function again to retry.

Note

On Windows the function waits up to 3 seconds for the Bluetooth adapter to answer, because the capabilities are read from it. An adapter that answers later still sets them and reports its state to the callback set with bluetooth_set_callback_state_changed.

Note

On iOS and macOS the function does not show the Bluetooth permission prompt. While the user has not answered it, Bluetooth stays unavailable until you call bluetooth_permission_request.


Syntax:

bluetooth_initialize()


Returns:

Boolean

true if the extension is running, otherwise false.


Example:

if (!bluetooth_initialize())
{
    show_debug_message($"Bluetooth could not start: {bluetooth_last_error_message()}");
    exit;
}

if (!bluetooth_feature_is_supported(BluetoothFeature.LeCentral))
{
    show_debug_message("This device cannot act as an LE client");
}
The above code initialises the extension in the Create Event of a controller object. If the backend could not be started, the reason is read with bluetooth_last_error_message and the event ends there. Otherwise bluetooth_feature_is_supported is used to check whether the device can scan for and connect to LE devices.

bluetooth_shutdown¶

This function stops the extension. It ends every connection, scan, advertisement and server, and frees every value still held for bluetooth_value_fetch. Every device, connection and value handle the extension gave out is no longer valid afterwards.

Every callback that is still waiting for the outcome of an operation (a connect, a read, a pairing, a permission or enable request, and so on) is called once with BluetoothError.NotInitialized. Every event callback you passed to a call that starts something, such as the on_found of a scan or the on_disconnected of a connection, is dropped without being called. The callback set with bluetooth_set_callback_state_changed stays registered, so it is used again after the next call to bluetooth_initialize.

You should call this function when the game no longer needs Bluetooth, for example in the Clean Up Event of the object that initialised it. Calling it when the extension is not running does nothing.


Syntax:

bluetooth_shutdown()


Returns:

N/A


Example:

if (bluetooth_is_initialized())
{
    bluetooth_shutdown();
}
The above code, placed in the Clean Up Event of the controller object, stops the extension if it is running. Any operation still in progress reports BluetoothError.NotInitialized to its callback, and no event callback is called.

bluetooth_is_initialized¶

This function checks whether the extension is running. It returns true after a successful call to bluetooth_initialize and until bluetooth_shutdown is called, and false before that, after it, or when bluetooth_initialize failed.


Syntax:

bluetooth_is_initialized()


Returns:

Boolean

true if the extension is running, otherwise false.


Example:

if (!bluetooth_is_initialized())
{
    bluetooth_initialize();
}
The above code initialises the extension only when it is not already running.

bluetooth_last_error_code¶

This function returns the error code of the most recent call that failed. Every function that can fail sets it when it fails: a function that returns a BluetoothError returns the same code, bluetooth_le_connect, bluetooth_classic_connect, bluetooth_device_from_id, bluetooth_le_service_find, bluetooth_le_characteristic_find and bluetooth_le_descriptor_find return 0, and bluetooth_initialize returns false.

A call that succeeds leaves the last error as it was, so you should read it straight after the call that failed, not to check whether a call succeeded. It is BluetoothError.Ok until the first failure. The outcome of an operation that completes later is reported to its callback in the callback's own error_code argument, not here.

Use bluetooth_last_error_message to get a description of the same failure.


Syntax:

bluetooth_last_error_code()


Returns:

BluetoothError

The error code of the most recent failed call.


Example:

var _error = bluetooth_request_enable(on_enable);
if (_error != BluetoothError.Ok)
{
    var _code = bluetooth_last_error_code();
    show_debug_message($"Request failed with code {_code}: {bluetooth_last_error_message()}");
}
The above code asks the user to turn the Bluetooth radio on and, when the request cannot start, reads the code and the description of the failure.

bluetooth_last_error_message¶

This function returns a description of the most recent call that failed, the same failure bluetooth_last_error_code returns the code of. The text comes from the extension or the platform and is meant for logs and debugging, not for the player; it is not localised and can differ between platforms for the same code.

Like the code, the message is set only when a call fails, so it still describes an earlier failure after a call that succeeds. It is an empty string until the first failure.


Syntax:

bluetooth_last_error_message()


Returns:

String

The description of the most recent failed call.


Example:

if (!bluetooth_initialize())
{
    show_debug_message($"Bluetooth could not start: {bluetooth_last_error_message()}");
}
The above code writes the reason to the output log when the extension could not be initialised.

bluetooth_feature_is_supported¶

This function checks whether the current platform and Bluetooth adapter can do the given feature. It is the one capability query of the extension: use it to decide which parts of your game's Bluetooth support to offer before you call the functions that need them. A function that uses a feature the platform cannot do returns BluetoothError.NotSupported.

The function returns false before bluetooth_initialize has been called, on a device without Bluetooth, and for a value that is not a BluetoothFeature member.

The table below shows what each platform can do when its hardware allows it. "Adapter" means the answer depends on the Bluetooth adapter or the OS version of the device the game runs on.

Feature Windows macOS iOS Android
LeCentral Adapter Yes Yes Adapter
LePassiveScan Adapter No No No
LeScanMode No No No Yes
LeAdvertise, LeAdvertiseName, LeAdvertiseServiceUuids Adapter Yes Yes Adapter
LeAdvertiseServiceData, LeAdvertiseManufacturerData, LeAdvertiseTxPower, LeAdvertiseIncludeTxPower, LeAdvertiseNonConnectable Adapter No No Adapter
LeServer Adapter Yes Yes Adapter
LeServerDescriptorRequests Adapter No No Adapter
LeServerSignedWrite, LeServerConnectionEvents, LePairing No No No Adapter
Classic, ClassicServer, ClassicPairing Adapter Yes No Adapter
ClassicDiscoverable Adapter No No Adapter
ClassicDiscoverableStop Adapter No No No
PermissionRequest No Yes Yes Android 6+
LeMtuRequest No No No Adapter
LeReadRssi No Yes Yes Adapter
LeConnectionPriority Adapter No No Adapter
RequestEnable Adapter No No Adapter
PairedDevicesQuery Adapter Yes No Adapter

Note

On Windows the answers come from the adapter, which bluetooth_initialize queries. Ask after it has been called, and ask again when the state callback reports a change, since an adapter that is added or removed changes them.


Syntax:

bluetooth_feature_is_supported(feature)
Argument Type Description
feature BluetoothFeature The feature to check.


Returns:

Boolean

true if the platform and adapter can do the feature, otherwise false.


Example:

can_advertise = bluetooth_feature_is_supported(BluetoothFeature.LeAdvertise);
can_send_manufacturer_data = bluetooth_feature_is_supported(BluetoothFeature.LeAdvertiseManufacturerData);

if (can_advertise && !can_send_manufacturer_data)
{
    show_debug_message("Advertising without manufacturer data on this platform");
}
The above code checks whether the game can advertise and whether the advertisement can carry manufacturer data, and stores both answers in instance variables. On a platform that can advertise but cannot send manufacturer data, such as iOS, a message is written to the output log.

bluetooth_permission_get_status¶

This function returns whether the game has the Bluetooth permissions the platform needs. It does not ask the user; use bluetooth_permission_request for that.

The function returns BluetoothPermissionStatus.Unknown before bluetooth_initialize has been called.

Note

On Windows the function always returns BluetoothPermissionStatus.Granted, since a desktop app needs no Bluetooth permission.

Note

On Android the function returns BluetoothPermissionStatus.Granted when every runtime permission the current Android version needs is granted: BLUETOOTH_SCAN, BLUETOOTH_CONNECT and BLUETOOTH_ADVERTISE from Android 12, ACCESS_FINE_LOCATION on Android 6 to 11. Android cannot tell a permission that was never asked for from one that was refused, so the extension remembers that it asked: the status is BluetoothPermissionStatus.Unknown until bluetooth_permission_request has been called once, and BluetoothPermissionStatus.Denied after that while a permission is missing. Clearing the app's data resets it.

Note

On iOS and macOS the function reports the app's Bluetooth authorisation: BluetoothPermissionStatus.Unknown until the user has answered the prompt that bluetooth_permission_request shows, and BluetoothPermissionStatus.Denied when the user refused it or it is restricted on the device.


Syntax:

bluetooth_permission_get_status()


Returns:

BluetoothPermissionStatus

The game's Bluetooth permission status.


Example:

var _status = bluetooth_permission_get_status();
if (_status == BluetoothPermissionStatus.Denied)
{
    show_debug_message("Bluetooth permission was refused, enable it in the system settings");
}
The above code reads the permission status and writes a message to the output log when the permission was refused.

bluetooth_permission_request¶

This function asks for the Bluetooth permissions the platform needs, showing the system prompt when the user has not answered it yet. The callback is called once with the answer: when the user answers the prompt, or without a prompt when the answer is already known.

The callback's error_code is BluetoothError.Ok whenever the request was answered, also when the user refused it, so check its status argument to see whether the permission was granted. If you call this function again while the prompt is still up, no second prompt is shown and both callbacks get the same answer. If bluetooth_shutdown is called before the answer, the callback is called with BluetoothError.NotInitialized and BluetoothPermissionStatus.Unknown.

The function returns a BluetoothError. It returns BluetoothError.NotInitialized before bluetooth_initialize has been called, and on Android BluetoothError.OperationFailed when the prompt cannot be shown. The reason is then in bluetooth_last_error_code and bluetooth_last_error_message, and the callback is never called.

After the user answers, the callback set with bluetooth_set_callback_state_changed reports the new adapter state on Android, iOS and macOS.

Note

On Windows no permission is needed: the callback is called with BluetoothPermissionStatus.Granted without a prompt.

Note

On Android 12 and later the function asks for BLUETOOTH_SCAN, BLUETOOTH_CONNECT and BLUETOOTH_ADVERTISE; on Android 6 to 11 it asks for ACCESS_FINE_LOCATION and ACCESS_COARSE_LOCATION. Before Android 6 the permissions are granted at install time and the callback is called without a prompt. The permissions must be declared in the game's manifest, see Platform Setup.

Important

On iOS and macOS the system prompt is shown only by this function. Until the user has answered it, every function that uses Bluetooth returns BluetoothError.PermissionDenied and the adapter state is BluetoothState.Unauthorized, as on Android without the runtime permissions. Once it has been answered, later calls report the answer without a prompt.

This function operates asynchronously, which means that it does not immediately return the requested result. Instead, upon completion of the task, it will trigger the Callback.


Syntax:

bluetooth_permission_request(callback)
Argument Type Description
callback Function The function to call once with the answer.


Returns:

BluetoothError

BluetoothError.Ok if the request was made, otherwise the reason it was not.


Triggers:

Callback

Called once, when the request is answered or Bluetooth is shut down before the answer.

Key Type Description
error_code BluetoothError BluetoothError.Ok if the request was answered, otherwise BluetoothError.NotInitialized.
message String A description of the failure, or an empty string when the request was answered.
status BluetoothPermissionStatus The permission status after the answer.


Example:

var _error = bluetooth_permission_request(function(_error_code, _message, _status)
{
    if (_error_code != BluetoothError.Ok)
    {
        show_debug_message($"Permission request failed: {_message}");
        return;
    }

    bluetooth_allowed = (_status == BluetoothPermissionStatus.Granted);
    show_debug_message($"Bluetooth permission granted: {bluetooth_allowed}");
});

if (_error != BluetoothError.Ok)
{
    show_debug_message($"Permission request did not start: {bluetooth_last_error_message()}");
}
The above code asks for the Bluetooth permissions. When the request is answered, the instance variable bluetooth_allowed is set to whether the permission was granted; when Bluetooth was shut down before the answer, the message is written to the output log instead. If the request could not be made at all, the reason is read with bluetooth_last_error_message and the callback is never called.

bluetooth_request_enable¶

This function asks the user to turn the Bluetooth radio on. The callback is called once with the outcome: BluetoothError.Ok when the radio is on, BluetoothError.BluetoothDisabled when the user declined or the radio stayed off, BluetoothError.PermissionDenied when the system refused the request, and BluetoothError.NotInitialized when bluetooth_shutdown is called before the answer. When the radio is already on, the callback is called with BluetoothError.Ok without asking the user.

If you call this function again while a request is still waiting, no second request is made and both callbacks get the same outcome.

The function returns a BluetoothError: BluetoothError.NotInitialized before bluetooth_initialize has been called, BluetoothError.NotSupported when the platform cannot turn the radio on (see BluetoothFeature.RequestEnable), BluetoothError.PermissionDenied on Android 12 and later without the BLUETOOTH_CONNECT permission, and BluetoothError.OperationFailed when the request cannot be made. The reason is then in bluetooth_last_error_code and bluetooth_last_error_message, and the callback is never called.

Note

On Android the function shows the system dialog that asks the user to turn Bluetooth on. From Android 12 it needs the BLUETOOTH_CONNECT permission, so call bluetooth_permission_request first.

Note

On Windows the function asks for access to the radio and switches it on, without a dialog of its own. The callback can also report BluetoothError.OperationFailed when Windows fails the request, and the function returns BluetoothError.NotSupported when there is no Bluetooth radio.

Note

iOS and macOS have no way for an app to turn the radio on, so the function always returns BluetoothError.NotSupported there. Ask the player to turn Bluetooth on in the system settings instead.

This function operates asynchronously, which means that it does not immediately return the requested result. Instead, upon completion of the task, it will trigger the Callback.


Syntax:

bluetooth_request_enable(callback)
Argument Type Description
callback Function The function to call once with the outcome.


Returns:

BluetoothError

BluetoothError.Ok if the request was made, otherwise the reason it was not.


Triggers:

Callback

Called once, when the radio is on, the request is declined or fails, or Bluetooth is shut down before the answer.

Key Type Description
error_code BluetoothError BluetoothError.Ok if the radio is on, otherwise the reason it is not.
message String A description of the failure, or an empty string on success.


Example:

if (bluetooth_feature_is_supported(BluetoothFeature.RequestEnable))
{
    var _error = bluetooth_request_enable(function(_error_code, _message)
    {
        if (_error_code != BluetoothError.Ok)
        {
            show_debug_message($"Bluetooth is still off: {_message}");
            return;
        }
        show_debug_message("Bluetooth is on");
    });

    if (_error != BluetoothError.Ok)
    {
        show_debug_message($"Enable request did not start: {bluetooth_last_error_message()}");
    }
}
else
{
    show_debug_message("Please turn Bluetooth on in the system settings");
}
The above code first checks with bluetooth_feature_is_supported whether the platform can turn the radio on. If it can, the user is asked to turn it on and the callback writes the outcome to the output log; if the request could not be made, the reason is read with bluetooth_last_error_message. On a platform that cannot do it, such as iOS, the player is told to use the system settings.

bluetooth_value_fetch¶

This function copies the bytes of a value into the given buffer, and frees the value. It is the one way to read every byte payload the extension delivers: an LE characteristic or descriptor read, a notification or indication, a write request to your LE server, and a chunk of data received on a Classic connection.

The callbacks that deliver bytes do not pass them directly. They pass a value handle and the number of bytes it holds, value and size, and you call this function with that handle to get the bytes. A handle can be fetched only once: the value is freed when it has been copied.

The buffer must have room for all size bytes at the given offset, that is, buffer_get_size of the buffer must be at least offset + size; the whole value is copied, never a part of it. A buffer_fixed buffer of size bytes is the usual choice.

The function returns BluetoothError.Ok when the bytes were copied. Otherwise it returns the reason, which is also in bluetooth_last_error_code and bluetooth_last_error_message:

  • BluetoothError.InvalidHandle for a value that is unknown, has already been fetched or released, or has expired. A failed read passes the value 0, which is always unknown.
  • BluetoothError.InvalidArgument for a buffer that is too small. Nothing is copied and the value is kept, so you can call the function again with a larger buffer, or free it with bluetooth_value_release.

The bytes are written straight into the buffer's memory, so neither the buffer's used size nor its seek position changes. Read them with buffer_peek, or with buffer_read after buffer_seek to offset. Call buffer_set_used_size before you pass the buffer to a function that only works on its used size, such as buffer_copy or buffer_save, or use bluetooth_value_to_buffer and bluetooth_value_append, which set the used size for you.

Usage Notes¶

The extension holds each value until you fetch or release it, within these limits:

  • A value expires 30 seconds after its callback was queued. Fetch it in the callback that delivers it.
  • At most 256 values from LE reads and notifications are held. Past that, the oldest of them is dropped.
  • The value of a write request to your LE server is freed with its request, when you answer it with bluetooth_le_server_respond_write, so fetch it before you answer.
  • The values of a Classic connection count toward a limit of 1 MiB per connection (see bluetooth_classic_connect). While its unfetched values hold more than that, Windows and Android stop reading from the peer until some are fetched or released; macOS ends the connection with BluetoothError.Disconnected. A Classic value that expires unfetched also ends its connection with BluetoothError.Disconnected, rather than leave a gap in the data.
  • A value stays available after its connection ends, so bytes delivered just before a disconnect can still be fetched.
  • bluetooth_shutdown frees every value.

Use bluetooth_value_release to free a value whose bytes you do not need.


Syntax:

bluetooth_value_fetch(value, out_data, offset)
Argument Type Description
value Real The value handle a callback delivered.
out_data Buffer The buffer to copy the bytes into.
offset Real The position in the buffer to copy the bytes to (in bytes).


Returns:

BluetoothError

BluetoothError.Ok if the bytes were copied, otherwise the reason they were not.


Example:

var _error = bluetooth_le_characteristic_read(characteristic, function(_error_code, _message, _characteristic, _value, _size)
{
    if (_error_code != BluetoothError.Ok)
    {
        show_debug_message($"Read failed: {_message}");
        return;
    }

    var _buffer = buffer_create(max(_size, 1), buffer_fixed, 1);
    if (bluetooth_value_fetch(_value, _buffer, 0) != BluetoothError.Ok)
    {
        show_debug_message($"Fetch failed: {bluetooth_last_error_message()}");
    }
    else if (_size > 0)
    {
        var _first = buffer_peek(_buffer, 0, buffer_u8);
        show_debug_message($"Read {_size} bytes, the first is {_first}");
    }
    buffer_delete(_buffer);
});

if (_error != BluetoothError.Ok)
{
    show_debug_message($"Read did not start: {bluetooth_last_error_message()}");
}
The above code reads the characteristic stored in the instance variable characteristic with bluetooth_le_characteristic_read. When the read succeeds, a fixed buffer the size of the value is created (at least 1 byte, since a value can be empty) and bluetooth_value_fetch copies the bytes into it at offset 0, freeing the value. Since the buffer holds the whole value, the fetch can only fail for a value that has expired. The first byte is then read with buffer_peek, which reads the buffer's memory directly, and the buffer is deleted. If the read could not start, the reason is read with bluetooth_last_error_message and the callback is never called.

bluetooth_value_release¶

This function frees a value without copying its bytes. Use it for a value whose bytes you do not need, so that it does not count toward the limits described in bluetooth_value_fetch until it expires: on a Classic connection, this lets the connection keep receiving. Every callback that delivers a value should either fetch it or release it, including on an early return.

The function returns BluetoothError.Ok when the value was freed, and BluetoothError.InvalidHandle for a value that is unknown, has already been fetched or released, or has expired; the reason is then in bluetooth_last_error_message.


Syntax:

bluetooth_value_release(value)
Argument Type Description
value Real The value handle a callback delivered.


Returns:

BluetoothError

BluetoothError.Ok if the value was freed, otherwise BluetoothError.InvalidHandle.


Example:

measurement_buffer = buffer_create(64, buffer_fixed, 1);

on_measurement = function(_characteristic, _connection, _value, _size)
{
    if (_connection != connection || paused || _size > buffer_get_size(measurement_buffer))
    {
        bluetooth_value_release(_value);
        return;
    }

    if (bluetooth_value_fetch(_value, measurement_buffer, 0) != BluetoothError.Ok)
    {
        show_debug_message($"Fetch failed: {bluetooth_last_error_message()}");
        return;
    }
    measurement_size = _size;
};
The above code creates a 64-byte buffer and the method on_measurement, which is passed as the on_value callback of bluetooth_le_characteristic_subscribe. A value that arrives for a connection other than the one stored in connection, while the instance's paused flag is set, or that is too large for the buffer is freed with bluetooth_value_release without being read. Any other value is copied into the buffer with bluetooth_value_fetch; since the buffer is known to be large enough, the fetch can only fail for a value that has expired, and the failure is written to the output log. On success the number of bytes is kept in measurement_size.

bluetooth_value_to_buffer¶

This function copies a value into a new buffer. It fetches the value with bluetooth_value_fetch, which frees it, and sets the used size of the new buffer to the size of the value, so the buffer can be passed straight to functions that work on the used size, such as buffer_copy or buffer_save. You must delete the buffer when you no longer need it.

If the value cannot be fetched, the function returns -1 and leaves nothing for you to free; the reason, normally BluetoothError.InvalidHandle for a value that has expired or was already fetched, is in bluetooth_last_error_code and bluetooth_last_error_message.

Note

This function is a GML helper written in the GMBluetooth_helpers script that ships with the extension, not a function of the native extension. It calls only the public functions documented here.


Syntax:

bluetooth_value_to_buffer(value, size)
Argument Type Description
value Real The value handle a callback delivered.
size Real The size of the value (in bytes), as the callback reported it.


Returns:

Buffer or Real

The new buffer holding the value, or -1 if the value could not be fetched.


Example:

var _error = bluetooth_le_characteristic_read(battery_level, function(_error_code, _message, _characteristic, _value, _size)
{
    if (_error_code != BluetoothError.Ok)
    {
        show_debug_message($"Read failed: {_message}");
        return;
    }

    var _buffer = bluetooth_value_to_buffer(_value, _size);
    if (_buffer == -1)
    {
        show_debug_message($"Fetch failed: {bluetooth_last_error_message()}");
        return;
    }
    buffer_save(_buffer, "battery_level.bin");
    buffer_delete(_buffer);
});

if (_error != BluetoothError.Ok)
{
    show_debug_message($"Read did not start: {bluetooth_last_error_message()}");
}
The above code reads the characteristic stored in battery_level. On success the callback copies the value into a new buffer with bluetooth_value_to_buffer, saves it to a file with buffer_save, which writes the buffer's used size, and deletes the buffer. If the value could not be fetched, or the read failed or could not start, the reason is written to the output log instead.

bluetooth_value_append¶

This function adds a value to the end of the data in the given buffer. It grows the buffer when the value does not fit after the buffer's used size, fetches the value there with bluetooth_value_fetch, which frees it, and moves the used size past the new bytes. This makes it the simplest way to collect the chunks of a Classic connection, which arrive in order but with no message boundaries.

The function returns the BluetoothError of the fetch: BluetoothError.Ok when the bytes were added, otherwise the reason, which is also in bluetooth_last_error_code and bluetooth_last_error_message, normally BluetoothError.InvalidHandle for a value that has expired or was already fetched.

Note

This function is a GML helper written in the GMBluetooth_helpers script that ships with the extension, not a function of the native extension. It calls only the public functions documented here.


Syntax:

bluetooth_value_append(value, size, buffer)
Argument Type Description
value Real The value handle a callback delivered.
size Real The size of the value (in bytes), as the callback reported it.
buffer Buffer The buffer to add the bytes to, at its used size.


Returns:

BluetoothError

BluetoothError.Ok if the bytes were added, otherwise the reason they were not.


Example:

receive_buffer = buffer_create(1024, buffer_grow, 1);

on_data = function(_connection, _value, _size)
{
    if (_connection != connection)
    {
        bluetooth_value_release(_value);
        return;
    }

    if (bluetooth_value_append(_value, _size, receive_buffer) != BluetoothError.Ok)
    {
        show_debug_message($"Receive failed: {bluetooth_last_error_message()}");
        return;
    }
    show_debug_message($"{buffer_get_used_size(receive_buffer)} bytes received so far");
};
The above code creates a buffer for the bytes a Classic connection receives and the method on_data, which is passed as the on_data callback of bluetooth_classic_connect. A chunk for a connection other than the one stored in connection is freed with bluetooth_value_release. Any other chunk is added to the end of receive_buffer with bluetooth_value_append, which grows the buffer when needed and moves its used size, so the game can look for complete messages in the buffer's used bytes.

bluetooth_set_callback_state_changed¶

This function sets the function to call when the state of the local Bluetooth adapter changes, for example when the user turns Bluetooth on or off. It replaces the callback set by an earlier call. It is the one global callback of the extension: every other event is passed to the call that starts its subject, such as a scan or a connection.

The callback is called with the current state when you set it, again when bluetooth_initialize succeeds, and then whenever the state changes. Before bluetooth_initialize the current state is BluetoothState.Unknown. The callback stays set across bluetooth_shutdown and the next bluetooth_initialize, until you remove it with bluetooth_remove_callback_state_changed.

When the state becomes anything but BluetoothState.PoweredOn or BluetoothState.Unknown, everything that was running ends before the callback is called: see BluetoothState.

The function always returns true.

Note

On Android the callback is also called after the user answers bluetooth_permission_request. From Android 12, a radio that is on reports BluetoothState.Unauthorized while the game does not have the BLUETOOTH_SCAN and BLUETOOTH_CONNECT permissions.

Note

On iOS and macOS the state is BluetoothState.Unauthorized until the user has answered the prompt of bluetooth_permission_request, and the callback reports the state again once the user has answered.

This function operates asynchronously, which means that it does not immediately return the requested result. Instead, upon completion of the task, it will trigger the Callback.


Syntax:

bluetooth_set_callback_state_changed(callback)
Argument Type Description
callback Function The function to call with the adapter state.


Returns:

Boolean

Always true.


Triggers:

Callback

Called once when the callback is set, and then whenever the state of the local Bluetooth adapter changes.

Key Type Description
state BluetoothState The new state of the local Bluetooth adapter.


Example:

bluetooth_set_callback_state_changed(function(_state)
{
    bluetooth_ready = (_state == BluetoothState.PoweredOn);
    if (_state == BluetoothState.PoweredOff)
    {
        show_debug_message("Bluetooth is off");
    }
});
The above code sets a callback that keeps the instance variable bluetooth_ready up to date with whether the adapter is on and usable, and writes a message to the output log when it is turned off.

BluetoothError¶

This enum holds the result codes of the extension. Every function that can fail returns one of them, except those that return a handle: bluetooth_le_connect and bluetooth_classic_connect (so that a disconnect can cancel a connect still in progress), bluetooth_device_from_id, bluetooth_le_service_find, bluetooth_le_characteristic_find and bluetooth_le_descriptor_find, which return 0 when they fail. After a failed call, bluetooth_last_error_code returns the code and bluetooth_last_error_message describes it. A call that fails never calls its callbacks.

A callback that reports the outcome of an operation receives one of these codes as its first argument, error_code, followed by a message that describes a failure. An event that cannot fail, such as a device found by a scan, carries data only.

The same condition fails with the same code on every platform, and these conditions are checked before anything starts, so they come back from the call itself:

Condition Code
A handle that is not, or is no longer, valid InvalidHandle
A device of the wrong transport, or another bad argument InvalidArgument
The radio is off or resetting BluetoothDisabled
The permission is missing or was refused PermissionDenied
No Bluetooth hardware, or a feature the platform cannot do (see bluetooth_feature_is_supported) NotSupported
The LE server is not running OperationFailed
A start while it already runs, a subscribe while subscribed, a duplicate service, or a full send or notify queue Busy

A stop while nothing runs returns Ok and calls nothing. What the game ends fires no event: a stop or a disconnect that you ask for takes effect when the call returns, and no on_stopped or on_disconnected callback is called for it, nor for the centrals and the advertisement that bluetooth_le_server_stop ends.

An outcome the extension recognises reads the same on every platform: when the other device closes the link, the message is Remote device disconnected, when the radio turns off it is BluetoothDisabled with Bluetooth was turned off or became unavailable, and a Classic connect to a service the device does not offer fails with ConnectionFailed and The device does not offer service <uuid>, or nothing is listening on it. A failure the extension cannot classify carries the platform's own text, as <operation> failed (<code>): <system text>.

BluetoothState¶

This enum holds the states of the local Bluetooth adapter, which the callback set with bluetooth_set_callback_state_changed receives.

When the state becomes anything but PoweredOn or Unknown, everything running ends, before the state callback is called: each LE and Classic scan and the advertisement call their on_stopped with BluetoothError.BluetoothDisabled, each connection, LE or Classic, and each central of the LE server call their on_disconnected with BluetoothError.BluetoothDisabled, and a connect in progress, LE or Classic, fails with BluetoothError.BluetoothDisabled. Each server, LE and Classic, then calls its on_stopped with BluetoothError.BluetoothDisabled, after the on_disconnected of each central or connection it served; the LE server's services and attribute handles are gone. Discoverability ends too, and its on_stopped is called with BluetoothError.BluetoothDisabled (see bluetooth_classic_discoverable_start). Nothing restarts when the radio comes back: start what you need again once the state is PoweredOn.

These constants are referenced by the following functions:

  • bluetooth_set_callback_state_changed


Member Description
Unknown The state is not known yet, for example before bluetooth_initialize or while the platform is starting. A scan started now begins once the radio is ready.
Resetting The adapter is changing state, for example turning on or off. Calls that use the radio return BluetoothError.BluetoothDisabled while it lasts.
Unsupported The device has no Bluetooth hardware the extension can use.
Unauthorized The game is not allowed to use Bluetooth: the permission has not been granted yet or was refused.
PoweredOff The Bluetooth radio is off or disabled.
PoweredOn The Bluetooth radio is on and the game can use it.

BluetoothConnectOptions¶

This struct says how bluetooth_le_connect and bluetooth_classic_connect run a connect. You create it with new BluetoothConnectOptions(); a variable left undefined takes its default, and you can pass undefined instead of the struct to use the defaults for everything.

This struct is referenced by the following functions:

  • bluetooth_classic_connect
  • bluetooth_le_connect


Member Type Description
timeout_ms Real The whole time from the call to an open link (in milliseconds), a pairing prompt included: 1000 to 300000, or undefined for 15000. A connect that is still not open when it runs out fails with BluetoothError.Timeout on every platform; a value outside the range makes the connect return 0 with BluetoothError.InvalidArgument.
